# 开发计划文档规范（plan-doc）

> **定位**：DL 在**阶段4**生成开发计划文档的操作手册。  
> **[项目负责人]审核依据**：[[quality-gate-checklists]] 第五章。

---

## 一、触发开发计划模式的条件

满足以下**任一条件**，必须启用主计划 + 子文档体系：

| # | 条件 |
|---|------|
| 1 | 功能包含独立 GPO 类型（每种 GPO 独立一份子文档） |
| 2 | 功能包含独立 Ability/AE 效果系统 |
| 3 | 需新建或修改已有 System 的挂载逻辑 |
| 4 | 功能涉及场景建设 |
| 5 | 功能包含模式系统主控（ServerMode + ClientMode） |

> **特别规则**：拾取物功能必须拆为「GPO拾取物文档」+「Effect效果文档」两份，不得合并。

---

## 二、文档体系与命名规则

> ⚠️ **强制路径约束**：所有功能文档必须存放在 `docs/GamePlay_Dev/{功能名}/`。**禁止**以 Agent 角色命名（如 `Dev_Lead/`、`GPO/`），也禁止放在 `agents/` 目录下。

```
docs/GamePlay_Dev/{功能名}/
  ├── {功能名}开发计划.md            ← 主计划（DL 编写，存放于功能目录）
  └── /技术文档/
      ├── README.md                                     ← 子文档索引
      ├── {功能名}-模式系统.md                             ← DL负责
      ├── {功能名}-{GPO类型}.md                            ← GPO 工程师负责
      ├── {功能名}-{Ability类型}.md                        ← Ability 工程师负责
      └── {功能名}-场景建设.md                             ← 场景建设工程师负责
```

---

## 三、主计划五要素（M-01 ~ M-03）

主计划只写**体验目标与全局导航**，不写具体实现（实现细节放子文档）。

| 编号       | 内容 | 关键要求 |
|----------|------|---------|
| **M-01** | 游戏主循环结构图（ASCII） | ★ 必须放文档最顶部；每个节点标注子系统名和子文档链接 |
| **M-02** | 开发阶段 × 体验节点总览 | ★ 放在 M-01 之后；Phase 与用户体验节点交替排列（见下方格式） |
| **M-03** | 技术子文档索引 | 文档名 / 负责 Agent / 职责范围 / 状态 |

**M-02 体验节点格式（强制）**：

> ⚠️ 格式必须严格遵守，因为 `session-sync.sh ux --init` 会自动解析此区块导入 active.md 里程碑。

```markdown
## M-02 开发阶段 × 体验节点

### Phase 1 — {阶段名称}

| 体验节点 | 验收目标 | 负责 Agent |
|---------|---------|-----------|
| UX-1 {简述} | {可验收的一句话目标} | [{Agent}] |
| UX-2 {简述} | {可验收的一句话目标} | [{Agent}] |

**→ Phase 1 完成 → 用户确认 UX-1~UX-2 → 进入 Phase 2**

### Phase 2 — {阶段名称}

| 体验节点 | 验收目标 | 负责 Agent |
|---------|---------|-----------|
| UX-3 {简述} | {可验收的一句话目标} | [{Agent}] |
```

**格式要求（违反将导致 `ux --init` 导入失败）：**

| 要素 | 要求 |
|------|------|
| Phase 标题 | `### Phase N — {名称}`（三级标题，N 从 1 开始递增） |
| 表头 | `\| 体验节点 \| 验收目标 \| 负责 Agent \|`（精确三列，顺序固定） |
| UX 项 | `\| UX-N {简述} \| {目标} \| [{Agent}] \|`（N 全局唯一递增） |
| Phase 结束语 | `**→ Phase N 完成 → 用户确认 UX-X~UX-Y → 进入 Phase N+1**`（可选但推荐） |

**Phase 4 阶段完成后，[项目负责人] 必须执行：**
```bash
session-sync.sh ux --init   # 从开发计划自动导入里程碑到 active.md
```

## 四、子文档五要素（S-01 ~ S-09）

每份子文档**必须包含以下九大要素**（缺一不通过[项目负责人]审核）。**专职 Agent 填充后，所有要素必须提供实际内容，不允许留占位符。**

| 编号       | 要素          | 说明                                             |
|----------|-------------|------------------------------------------------|
| **S-01** | 作者签署        | 负责填充本文档的专职 Agent（GPO工程师 / Ability工程师 / 场景建设工程师）  |
| **S-02** | 参考文档        | 填充前参考了哪些规范（格式见 technical-doc-format.md §三）      |
| **S-03** | 功能需求        | 一句话：玩家拿到这个单模块会有怎样的体验？                          |
| **S-04** | 功能定位        | 一句话：这份文档解决什么问题，职责边界在哪                          |
| **S-05** | 文件清单        | .cs 文件 + CSV 路径 + 状态（新建/修改/复用），分层表格格式（见 §二）     |
| **S-06** | ASCII 交互链路图 | 核心流程时序图；涉及玩家操作时必须覆盖 `输入→CMD→服务端→RPC→客户端表现` 全链路 |
| **S-07** | 灰盒资源占位    | 每个新视觉对象：形状/颜色（_BaseColor RGBA）/尺寸/挂点偏移，四项缺一退回  |
| **S-08** | 边界条件        | 依赖的外部接口 + 禁止做的事 + 边界定义文档引用                     |
| **S-09** | 验收标准        | ≥3 条可测试行为描述，覆盖编译/运行时/功能三层                      |

---

## 五、灰盒资源占位（阶段4强制）

每个新视觉对象（GPO / 特效 / UI）必须在主计划或子文档中明确 4 项：

| 字段 | 要求 |
|------|------|
| 形状 | Cube / Sphere / Cylinder / Capsule / Plane |
| 颜色 | `_BaseColor RGBA`，如 `(1, 0.3, 0.3, 1)` |
| 尺寸 | 三轴尺寸 + 单位米，如 `2m × 1m × 2m` |
| 挂点偏移 | 相对 Entity 根节点偏移，如 `(0, 1, 0)` |

> ⚠️ 只写"Cube 占位"而缺尺寸和位置的描述，不通过审核。

## 六、多 Agent 分工（任务分发格式）

DL 在阶段2完成后输出子任务分发说明：

```
【子任务分发说明 — {功能名}】
子任务1 - GPO 工程师：
  负责：[GPO 类型]
  子文档：docs/GamePlay_Dev/{功能名}/技术文档/{功能名}-{GPO类型}.md
  接口约定：GPO Sign = {Sign}；需 Ability Agent 提供 AB Sign + InData

子任务2 - Ability 工程师：
  负责：[AB/AE 类型]
  子文档：docs/GamePlay_Dev/{功能名}/技术文档/{功能名}-{Ability类型}.md
  接口约定：完成后提供调用示例，供 GPO 工程师填充预留桩

子任务3 - 场景建设工程师：
  负责：场景建设
  子文档：docs/GamePlay_Dev/{功能名}/技术文档/{功能名}-场景建设.md
  接口约定：需 GPO 工程师提供 SceneGPO Sign
```

## 七、关键架构规则

- **GPO 类型决定 GPOM 归属**：T-GoldenEgg → `GPOM_GoldenEgg.cs`，禁止混入 `GPOM_{模式名}Set.cs`
- **Component 挂载只能在自身 System 内部**：外部 System 禁止注入组件
- **架构变更必须归档 ADR**：子文档末尾补充 `ADR-{N}` 章节（变更原因 + 用户授权 + 影响范围）

---

## 八、跨文档一致性检查（[项目负责人] Round 2）

| 检查项 | 要求 |
|-------|------|
| Rpc 发送主体 | 同一 Rpc 在不同文档中发送方身份不得矛盾 |
| GPO 类型名 | 跨文档引用同一 GPO 时类型名必须完全一致 |
| System 状态 | 同一 System 的新建/修改状态不得在不同文档中矛盾 |
| 文件不重复声明 | 同一 .cs 不得在多份子文档中均标注"新建" |
| 接口已履行 | GPO 预留桩已被 Ability 提供的调用示例填充 |

---

## 九、阶段4完成后强制等待（阶段5门控）

DL 输出主计划 + 子文档后，**[项目负责人] 必须**：

**Step 1: 导入里程碑**
```bash
session-sync.sh ux --init   # 从 M-02 自动导入 Phase/UX 表格到 active.md
```

**Step 2: 通过 `ask_user` 确认以下五项**，全部通过才能进入开发：

1. M-02 体验节点流程图是否在文档顶部、AI/用户阶段交替清晰
2. 文件清单完整（新增/修改均已覆盖）
3. 技术方案方向符合项目架构
4. 美术资产灰盒方案明确（形状/颜色/尺寸齐全）
5. UI 资产灰盒方案明确
