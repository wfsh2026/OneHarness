# 核心循环完整性检查框架

> 💡 **认知框架（Skill）** — 教你如何运用核心循环规则进行思考
>
> **权威定义**：[[GamePlay_Dev/core-rules]] §1.4-1.6
> （8 要素定义、交互链路模板、Checklist 以该文件为准，本文件不重复）

---

## 什么时候需要这个 Skill

- 制定**执行计划**时 → 用来验证阶段划分是否遗漏环节
- 编写**技术文档**时 → 用来检查交互链路是否完整
- **阶段一确定前** → 用来决定哪些功能必须纳入最小核心循环

---

## 思维方法

### 步骤 1：画出功能的核心链路图

拿到功能需求后，先不管阶段划分，画出**从触发到结束**的完整链路：

```
用户操作 → 客户端响应 → 上行消息 → 服务端处理 → 下行消息 → 客户端表现 → 结束/循环
```

> **常见错误**：只画了服务端逻辑（⑤），跳过了客户端 UI（③）和消息链路（④⑥）

### 步骤 2：逐项对照 8 要素 Checklist

打开 `core-rules.md §1.6` 的 Checklist，逐行检查：
- 每一项标记为 ✅（已定义）或 ❌（未定义）
- 若 **②玩家输入** 或 **③客户端UI** 标记为 ❌ 但功能确实需要 → **强制纳入阶段一**

### 步骤 3：验证链路无断点

检查步骤 1 画出的链路图，确保：
- 每个 `→` 之间都有明确的消息类型（CMD / RPC / 事件）
- 没有"逻辑跳跃"（即中间步骤被跳过，例如直接从客户端操作到服务端状态变更）

---

## 常见误区

| 误区 | 后果 | 正确做法 |
|------|------|---------|
| "UI 是表现层，后面再做" | 玩家无法操作，核心循环断裂 | UI 交互属于核心循环，必须纳入阶段一 |
| "先做服务端逻辑再补消息" | CMD/RPC 设计被倒逼，消息结构不合理 | 消息链路与逻辑同步设计 |
| "循环出口不急" | 功能无法正常结束，状态机卡死 | 出口条件和触发条件同等重要 |
| "只涉及服务端不需要画链路" | 遗漏广播环节，其他客户端看不到变化 | 即使是纯服务端逻辑，也要确认是否需要 RPC 同步 |

---

## 自检问题

完成执行计划后，用以下问题自检：

1. 我画的链路图覆盖了 8 个要素中的几个？缺失的是什么？
2. 有没有哪个 `→` 是"想当然"的？中间的消息类型是否已明确？
3. 玩家从头到尾的操作体验是否连贯？有没有"等待黑盒"的环节？
