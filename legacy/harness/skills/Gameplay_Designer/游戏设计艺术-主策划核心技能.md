# 游戏设计艺术 — 主策划核心技能文档

> **来源**：Jesse Schell 《The Art of Game Design: A Book of Lenses》第三版  
> **文档性质**：主策划 AI 角色的技能内化文档，不是书籍摘要，是可直接用于设计决策的工作框架  
> **使用方式**：每次进入主策划角色时加载此文档，作为设计判断的底层依据

---

## 一、根本前提：设计师创造的是体验，不是游戏

这是整本书最核心的一句话，也是最容易被忽视的一句话。

```
游戏设计师的工作 ≠ 设计规则、机制、系统
游戏设计师的工作 = 设计玩家在游戏过程中的感受
```

**实际操作含义：**

在任何设计讨论中，第一个问题永远是：
> "玩家在这个时刻感受到什么？"

而不是：
> "这个系统应该怎么运作？"

系统是手段，体验是目的。如果一个机制无法被追溯到一个具体的玩家体验目标，这个机制的存在就值得怀疑。

## 二、透镜方法论（Lens System）

Schell 用 100 个"透镜"作为设计工具。透镜不是规则，是**一组问题**——从不同角度审视同一个设计，发现你在单一视角下看不到的问题。

**主策划如何使用透镜：**

不是背诵所有 100 个透镜，而是掌握"切换视角"的习惯。当一个设计讨论陷入僵局时，换一个透镜提问，往往能打破僵局。

以下是对当前项目最相关的核心透镜分类：

---

### 2.1 体验类透镜（最高优先级）

#### 透镜：惊喜（Surprise）
> 游戏中有没有让玩家感到意外的时刻？意外是乐趣的核心来源之一。

设计检查问题：
- 玩家在第 N 次游玩时，还能遇到新鲜的事情吗？
- 哪些时刻是玩家预期不到的？
- 系统交互是否产生了设计者自己都没预料到的有趣结果？

#### 透镜：乐趣（Fun）
> 这个游戏有趣吗？——这个问题听起来简单，但必须反复追问。

Schell 对"乐趣"的定义：乐趣是伴随着惊喜的愉悦感。没有意外就没有乐趣。

设计检查问题：
- 把这个机制用文字描述给一个从没玩过游戏的人，他们会有兴趣吗？
- 这个设计的乐趣来源是什么？是掌控感、发现感、社交感，还是竞争感？
- 如果去掉这个系统，游戏会变得更不好玩吗？

#### 透镜：心流（Flow）
> 玩家是否处于"心流状态"——挑战恰好匹配能力，既不无聊也不焦虑？

Csikszentmihalyi 的心流理论在游戏设计中的应用：

```
焦虑区（挑战 >> 能力）
    ↑
心流区（挑战 ≈ 能力）← 目标区域
    ↓
无聊区（挑战 << 能力）
```

设计检查问题：
- 游戏早期是否存在"能力已远超挑战"的时间段？（无聊）
- 游戏中是否存在突然的难度峰值？（焦虑）
- 难度曲线是否随玩家成长平滑上升？

**对当前项目的直接应用：**  
PVE Roguelike 模式的词条构筑系统，本质上就是一个心流管理机制——玩家通过选词条不断提升能力，怪物难度也随回合数提升。关键设计问题是：两条曲线的斜率是否匹配？

---

### 2.2 玩家类透镜

#### 透镜：玩家（The Player）
> 你的玩家是谁？他们真正想要什么？

Schell 区分了玩家**表达的需求**和**真实的需求**：
- 玩家说"我要更强的武器" → 真实需求可能是"我要碾压感"
- 玩家说"游戏太难了" → 真实需求可能是"我要更清晰的反馈"

设计检查问题：
- 这个功能是在满足玩家说出口的需求，还是他们背后的真实需求？
- 目标用户群体（微信小游戏轻度用户）的注意力窗口有多长？
- 什么类型的玩家会对这个机制产生共鸣？

#### 透镜：四种乐趣类型（Bartle's Taxonomy 延伸）

Schell 在 Bartle 玩家类型基础上，将玩家动机归纳为：

| 动机类型 | 描述 | 对当前项目的对应设计 |
|---------|------|-------------------|
| 成就感 | 完成挑战、变得更强 | 词条构筑、通关回合数排行 |
| 探索欲 | 发现新内容、测试系统边界 | 元素派生链、词条组合 |
| 社交感 | 与他人互动、展示自己 | 多人联机、排行榜 |
| 竞争欲 | 击败他人 | PVP 模式、个人积分 |

**关键判断**：一个系统服务的是哪种动机？如果一个系统同时试图服务所有动机，它往往对任何一种都服务不好。

---

### 2.3 机制类透镜

#### 透镜：核心循环（The Loop）
> 游戏的核心反馈循环是什么？它是否足够紧凑、足够有趣？

Schell 的核心循环分析框架：

```
玩家做出决策
    ↓
游戏产生反馈
    ↓
玩家获得新信息
    ↓
玩家做出下一个决策（循环）
```

一个好的核心循环满足：
1. **紧凑**：从决策到反馈的时间间隔短
2. **清晰**：玩家能理解反馈与自己决策的因果关系
3. **有意义**：每次循环都让玩家产生新的策略判断

**对当前项目的直接应用：**

多武器 PVE 模式的核心循环应该是：
```
[走位聚怪] → [怪物被消灭] → [获得词条选择] → [BD 构筑决策] → [下一波更强感受] → 循环
```
如果这个循环不成立（比如词条对当局感受影响不明显），整个 Roguelike 设计就会失效。

#### 透镜：平衡（Balance）
> 游戏是否平衡？——但更重要的问题是：什么样的平衡才是对的？

Schell 区分了三种平衡：

| 平衡类型 | 描述 | 常见误区 |
|---------|------|---------|
| 公平平衡 | 所有选项在竞技场景中势均力敌 | PVP 必须追求，PVE 不必追求 |
| 挑战平衡 | 挑战难度与玩家当前能力匹配 | 动态难度设计的核心 |
| 选择平衡 | 没有"唯一最优解"，多种策略都可行 | Roguelike 词条设计的核心 |

**关键洞察**：在 PVE Roguelike 中，"公平平衡"是错误的目标。玩家需要感受到"我变得越来越强"——这本质上是一种刻意制造的不平衡。正确目标是"挑战平衡"和"选择平衡"。

#### 透镜：风险与回报（Risk and Reward）
> 游戏中的高风险选择，是否有与之匹配的高回报？

设计检查问题：
- 词条系统中，高品质词条是否带来了质变级别的回报？
- 玩家做出激进决策（如主动靠近 Boss 触发近战）时，是否有对应的高回报？
- 游戏中是否存在"安全无聊的最优策略"——玩家永远选最保险的选项？

### 2.4 叙事与体验感知类透镜

#### 透镜：故事（Story）
> 即使是没有剧情的游戏，也在讲故事——每局游戏就是一个故事。

Schell 的观点：游戏中的"故事"不一定是文字叙事，可以是玩家自己创造的经历叙事。

> "那一局我在最后一秒抓住了 Boss 的攻击间隙，把它打死了。"

这就是游戏自动生成的故事。设计师需要创造让这类"故事时刻"自然发生的系统条件。

设计检查问题：
- 游戏的哪个机制最容易产生玩家事后主动讲述的"高光时刻"？
- Boss 战是否有足够的阶段感，让玩家事后能复述"我是在第二阶段用火球连击搞定它的"？

#### 透镜：美感（Aesthetics）
> 游戏的视听表现是否在强化体验，而不是与体验割裂？

对于射击游戏，最关键的美感问题是**打击感**：
- 命中音效 → 是否清脆、有冲击力？
- 命中特效 → 是否清晰、能让玩家立刻感知到"打中了"？
- 飘字数字 → 是否足够大、颜色区分是否够清晰？

## 三、Schell 的设计推导方向（最重要的方法论）

```
❌ 错误方向（功能驱动）：
   设计一个系统 → 期望它带来体验

✅ 正确方向（体验驱动）：
   确定目标体验 → 反推需要什么系统 → 评估系统能否产生该体验
```

**实际操作步骤：**

1. 用一句话描述目标体验（必须包含玩家情绪，而非系统功能）
2. 列出"什么情况下玩家会产生这种情绪"
3. 设计能制造这些情况的系统
4. 原型验证：玩家在实际游玩中是否产生了预期情绪
5. 根据验证结果调整系统，而不是调整体验目标

## 四、Schell 的玩家体验四维模型（DICE）

Schell 将玩家体验分解为四个维度：

| 维度 | 英文 | 含义 | 设计师的工作 |
|------|------|------|------------|
| 机制 | Mechanics | 规则、系统、数值 | 确保逻辑自洽、平衡合理 |
| 故事 | Story | 叙事、角色、世界观 | 确保玩家行为与叙事一致 |
| 美感 | Aesthetics | 视觉、音效、手感 | 确保感官体验强化机制体验 |
| 技术 | Technology | 实现手段、平台限制 | 确保设计在技术约束内可实现 |

**关键原则**：四个维度必须互相支撑，不能割裂。

> 例：一个"爽快割草"的体验目标  
> - 机制：低操作密度、高输出数字、快速清屏  
> - 故事：玩家是强力英雄，怪物是杂兵炮灰  
> - 美感：命中特效满屏、音效密集爽脆、飘字足够大  
> - 技术：帧率稳定，不能因为特效太多而掉帧影响手感  

如果美感层面特效太弱，即使数值上玩家确实在碾压，主观感受也不会爽快。

## 五、主策划的核心工作：问对问题

Schell 整本书最终传递的不是"游戏设计的答案"，而是"游戏设计师需要问哪些问题"。

**主策划在每次设计讨论中必须问的五个问题：**

| 问题 | 目的 |
|------|------|
| 这个设计服务的是哪种玩家体验？ | 防止系统失去目的 |
| 玩家在这个时刻感受到什么？ | 把设计锚定在体验上 |
| 什么情况下这个设计会失败？ | 识别边界条件和风险 |
| 能不能更简单地实现同样的体验？ | 对抗复杂度膨胀 |
| 原型验证了哪些假设，推翻了哪些假设？ | 防止文档驱动的虚假确定性 |

## 六、Schell 的迭代观——为什么原型优先于文档

Schell 在书中明确说：

> "游戏设计师唯一真正的工具是迭代。你不可能在纸上把游戏设计正确，你只能把它玩正确。"

**对文档的正确定位：**

| 文档类型 | 正确用途 | 错误用途 |
|---------|---------|---------|
| 策划案 | 记录已验证的设计决策 | 作为开发的起点和蓝图 |
| 数值表 | 归档经过游玩调整后的参数 | 预先设计未经验证的数值 |
| 体验目标文档 | 作为所有迭代的评判标准 | 用来替代实际游玩验证 |

**迭代的最小单元：**

```
1. 提出一个可测试的体验假设
   例："如果词条效果足够明显，玩家在第3回合会感受到质变"

2. 做最小化原型验证这个假设
   例：临时把某个词条效果放大10倍，看玩家反应

3. 根据结果确认或推翻假设
   例："质变感来了，但太早了，应该在第5回合"

4. 将验证结果写入文档（而不是在游玩前写入文档）
```

## 七、对当前项目的直接诊断（主策划视角）

基于 Schell 的框架，对当前项目现状的判断：

### 已经做对的事
- 模式分类清晰（PVP/PVE双轨）——功能边界合理
- 核心循环结构存在（战斗→词条→下一回合）——骨架正确
- 元素派生链设计（灼烧→火球→陨石）——"探索欲"玩家动机有对应设计

### 需要重新审视的事

**问题1：体验目标从未被单独确立**  
现有策划案描述的是系统，不是体验。"割草爽快感"散落在各处，从未被明确定义成可以用来判断设计好坏的标准。

**问题2：数值是预设的，不是验证的**  
TTK 0.5~1s、命中率 85%——这些数字没有经过游玩验证，是估算值。Schell 会说：这些数字在第一次游玩之后会全部改变，那么为什么要花时间预设它们？

**问题3：核心循环的紧凑度未经验证**  
从"击杀怪物"到"感受到词条效果"之间的时间间隔是否足够短？这个问题只有原型能回答，文档无法回答。

## 八、主策划工作的启动清单

每次进入新的设计讨论时，按顺序确认以下项目：

```
□ 体验目标是否已经用一句话明确定义？
  （必须包含玩家情绪，而非系统功能描述）

□ 这次讨论的设计是否可以追溯到体验目标？
  （如果追溯不到，这个设计需要重新审视存在价值）

□ 是否有原型可以验证这个设计假设？
  （如果没有，下一步应该是做原型，而不是完善文档）

□ 玩家在这个设计的关键时刻感受到什么？
  （从玩家视角描述，而不是从系统视角描述）

□ 这个设计最可能在哪个边界条件下失败？
  （识别最大的设计风险）
```
