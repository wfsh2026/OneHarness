# 验证规则

开发完成前必须验证：

- 新增功能符合成功标准。
- 无效输入被正确处理。
- 修复漏洞时，先能复现，再验证修复后通过。
- 重构前后行为一致。
- 文档变更的入口、索引和引用路径可达。
- 子任务交付结果符合项目 wiki 子任务页。
- 多模块任务的接口契约、事件、数据结构、状态流或资源引用已集成验证。

## 验证记录

验证记录必须包含：

- 验证项。
- 命令或手动检查方式。
- 结果。
- 无法验证的原因。
- 未验证带来的风险。
- 子任务验证和主程集成验收的对应关系。

无法运行自动测试时，必须提供替代检查，不允许把未验证写成已通过。

## 输出收敛

验证命令必须保留有效证据，但默认不读取或回传大体量原始输出。

- 构建、测试、Unity 批处理、打包、静态扫描和日志分析命令可能产生大量输出时，先重定向到日志文件，再读取失败摘要、错误行、测试汇总或最后少量关键行。
- `git status`、`git diff`、`git show` 等仓库检查默认限定到本轮修改路径；需要全仓检查时，只汇总变更范围、数量和风险，不输出完整无关文件清单。
- 构建通过但存在大量重复 warning 时，验证记录只写通过结论、warning 类型或数量，不粘贴完整 warning 列表。
- Unity 测试优先读取测试结果 XML 或测试汇总；测试未启动时，只读取导致未启动的关键日志行和对应影响。
- 只有用户明确要求完整输出，或过滤后的摘要不足以定位失败原因时，才允许扩大读取范围；扩大读取时必须说明原因。

验证记录应同时说明原始日志位置、读取的摘要范围和最终判断，避免把“没有读取完整日志”误写成“没有验证”。
