# 意图识别与系统归属思维框架

> 💡 **认知框架（Skill）** — 教你如何快速识别需求涉及的系统
>
> **权威定义**：[[knowledge/system-map]] §三（关键词映射表 + 5 条识别原则）
> （关键词→系统映射以该文件为准，本文件不重复映射表）

---

## 什么时候需要这个 Skill

- 收到用户需求的**第一时间** → 用来判断应加载哪些文档
- 需求描述**模糊或跨系统**时 → 用来决定是否需要向用户确认
- 准备**新建 System/Component** 前 → 用来确认系统归属是否正确

---

## 思维方法（决策树）

```
收到用户需求
    │
    ├─ 步骤 1：提取关键词
    │    从用户输入中提取所有可能的系统关键词
    │
    ├─ 步骤 2：查映射表
    │    打开 system-map.md §三，逐行匹配关键词
    │    → 可能命中 0 个 / 1 个 / 多个系统
    │
    ├─ 步骤 3：歧义判断
    │    ├─ 命中 0 个 → 向用户确认需求属于什么系统
    │    ├─ 命中 1 个 → 加载对应文档，继续
    │    └─ 命中多个 → 进入步骤 4
    │
    ├─ 步骤 4：多系统处理
    │    ├─ 多个系统都需要 → 全部加载文档
    │    └─ 不确定哪个 → 向用户确认（不猜测！）
    │
    └─ 步骤 5：复用检查
         确定系统归属后，先检索已有实例/框架
         → 能复用 → 基于已有框架扩展
         → 不能复用 → 确认后新建
```

## 高危歧义场景（必须确认）

以下场景**禁止自行判断**，必须先向用户确认：

| 用户说了... | 可能是 A | 也可能是 B | 确认问题 |
|------------|---------|-----------|---------|
| "武器""飞行物" | GPO（独立单元） | 枪械/载具（外观包装） | "这是独立的 GPO 单元还是现有系统的外观？" |
| "刷怪""波次" | 新建 SpawnerSystem | 复用 T-GPOSpawner | "要用现有 GPOSpawner 框架还是新建？" |
| "升级""成长" | Ability 系统 | GPO 道具 + 数值叠加 | "升级是独立技能系统还是道具效果？" |
| "触发""机关" | GPO SceneElement | 全局事件系统 | "这个触发器是场景物件还是全局事件？" |

---

## 常见误区

| 误区 | 后果 | 正确做法 |
|------|------|---------|
| 看到"武器"就判定为枪械系统 | 可能是 GPO 悬浮武器，架构完全不同 | 先问"独立单元还是外观包装" |
| 需求涉及多系统但只加载了一个文档 | 遗漏另一个系统的约束规则 | 匹配到的系统全部加载文档 |
| 准备新建 System 但未检索已有实现 | 重复造轮子 | 先搜索项目中是否有类似实现 |

---

## 核心原则

> **宁可多问一句，不要猜错系统归属。**
> 猜错系统归属导致的返工成本远高于一次确认的时间成本。
