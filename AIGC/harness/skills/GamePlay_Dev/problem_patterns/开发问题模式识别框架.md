> 💡 **认知框架（Skill）** — 教你如何快速分类开发中遇到的问题并路由到正确文档
>
> **权威定义**：[[lessons-learned]]（问题路由表 + 历史复盘记录）

## 什么时候需要这个 Skill

- 开发过程中**出现问题**时 → 用来快速分类并找到对应规范
- **复盘阶段** → 用来判断经验教训应该沉淀到哪个文件
- 新 Agent 首次参与项目 → 了解常见踩坑点，预防性规避

## 常见问题模式（5 类高频问题）

### 模式1：系统归属误判

**典型案例**：悬浮武器误判为枪械系统改造，未询问"GPO 还是外观包装"

**识别信号**：
- 需求涉及"武器/飞行物/悬浮体"等歧义关键词
- 直接判断了系统归属而未向用户确认

**应对**：查 `system-map.md §三`，遇到歧义主动确认

---

### 模式2：忽略现有框架

**典型案例**：自建 WaveSpawner System 而非复用 GPOSpawner 框架

**识别信号**：
- 准备新建 System/Component 时
- 未先检索项目中是否已有类似功能的实现

**应对**：先搜索已有实例和框架，确认无法复用后才新建

---

### 模式3：交互链路遗漏

**典型案例**：三选一功能归入策略层，遗漏了 UI 交互链路

**识别信号**：
- 功能涉及玩家操作但未画出完整链路图
- 技术文档缺少 Input→CMD→RPC→Client 交互链路

**应对**：用核心循环 Checklist（`core-rules.md §1.6`）逐项验证

---

### 模式4：灰盒方案不完整

**典型案例**：灰盒方案只写"白色 Cube 占位"，缺少具体尺寸和挂点描述

**识别信号**：
- 灰盒描述中使用模糊表述（"类似XX大小"）
- 缺少颜色、尺寸、挂点三项中的任意一项

**应对**：用设计文档完整性框架补充（`设计文档完整性思维框架.md`）

---

### 模式5：流程跳步

**典型案例**：未等审阅信号直接执行了后续阶段的操作

**识别信号**：
- 跳过了 workflow 中定义的门控检查
- 未等待用户确认信号就进入下一阶段

**应对**：严格按 `workflow-dev.md` 的门控规则执行

## 问题处理决策树

```
发现问题
    │
    ├─ 步骤 1：对照 5 种模式，匹配问题类型
    │
    ├─ 步骤 2：查路由表（lessons-learned.md）
    │    → 找到对应的规范文档
    │
    ├─ 步骤 3：按规范修正
    │    → 修改代码/文档/计划
    │
    └─ 步骤 4：沉淀判断
         ├─ 已有模式覆盖 → 在对应规范文档中补充
         └─ 新类型问题 → 追加到 lessons-learned.md
```

## 预防性自检

在开始写代码前，快速过一遍这 5 个问题：

1. ❓ 我确认了系统归属吗？还是我在猜？
2. ❓ 我搜索过项目中的已有实现吗？
3. ❓ 我画了完整交互链路吗？有没有跳过 UI/消息层？
4. ❓ 灰盒/占位描述有具体数值吗？
5. ❓ 我在正确的阶段做正确的事吗？有没有跳步？

> **核心原则**：每个问题都应能归入已知模式。如果无法归类，说明需要扩展本框架。
