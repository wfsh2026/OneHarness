# 代码规范

> 该文档为项目代码规范与审核维度，包含架构、生命周期、数据所有权、Unity 编码与架构规范、命名规范与若干项目开发约束。

---

## 一、强制审核维度（逐条检查）

### 玩法架构使用规范
- **Manager**：仅管理 System 的创建/销毁。
- **System**：收集/操作组件，不写业务逻辑。
- **Component**：逻辑最小单元，通过事件间接通信。
  - 不得直接修改老组件。
  - 需复制并在新 System 中验证后方可替换。
  - 组件不能互相持有，只能通过事件（MsgRegister.Register 或 mySystem.Register）通信。
- **Entity**：不写逻辑，仅提供接口。
- **Base 类改动权限**：仅 Leader 可改，如 systembase、c_monster_base 等。
- **Asmdef（程序集） 改动权限**：仅 Leader 可新增、修改、删除。

---

## 三、生命周期与时序安全

> 必须检查：

- 对象是否明确：创建时机、初始化顺序、销毁与回收责任。
- 是否存在：Update 中隐式依赖初始化完成、构造函数 / Awake / Start 职责混乱。

> 推荐：

- 明确 Awake / Start / Clear 的职责。
- 用状态而不是 bool 标志位。

---

## 四、数据所有权与封装

> 必须检查：

- List / Dictionary 是否被直接暴露。
- 是否存在“返回内部容器引用”的行为。

> 推荐做法：

- 返回：IReadOnlyList / IReadOnlyCollection、Iterator / Copy。
- 所有 Add / Remove：只能通过拥有者类完成。

> 红线：

- 外部类随意修改核心集合。

## 五、C# Unity 编码与架构规范（Reference Document）

### 1. Unity 性能核心准则
- 严禁在 `Update`、`FixedUpdate` 或 `LateUpdate` 中进行会导致大量堆内存分配的操作（如 new 数组、字符串拼接、使用 LINQ）。
- 缓存组件引用：严禁在循环或 Update 中使用 `GetComponent`。所有引用必须在 `Awake` 或 `Start` 中缓存。
- 寻找对象的正确方式：严禁使用 `GameObject.Find()`。优先使用 `SerializeField` 拖拽引用或单例模式/依赖注入。
- 物理系统：物理计算必须放在 `FixedUpdate`。使用 NonAlloc 版本的物理 API（如 `Physics.RaycastNonAlloc`）。

### 2. 逻辑规范（性能 & 工程规范）
- 禁用 Find，射线必须设 `maxDistance`，客户端除 `Camera` 和 `LocalCharacter` 外，禁用 RayCast。
- `Update` 系列函数中不允许：
  - 每帧调用 RPC/CMD
  - 每帧调用 `GetComponent` / Load
  - 每帧创建 AB 对象或分配内存
- 禁止在线上战场过程中打 `Debug.Log`。
- 禁止 `MonoBehaviour.OnGUI`。
- 禁止直接使用 `GameObject.tag`。
- 字典 Key 禁止用 struct。
- 事件监听写在 OnAwake，事件派发不得写在 OnAwake。
- 坐标更新使用 `ientity.SetPoint()`，禁止直接赋值 `transform.position`。
- 协议 proto 的编写只能使用 C# 常规类型，禁止自己创建接口、class。
- 协议 proto 可以通过 `struct` 对数据类进行整理，但是只能是常规类型整理，且不能出现 struct 嵌套 struct。
- 在小游戏环境中，若新增了 runtime 所使用的资源，则需在 `MiniGameConfig` 配置项下方对应增加扩展名。
- Component 里的 `override void Sync(List<` 和 `override ITargetRpc SyncData()` 都为自己或其他玩家断线后会触发的逻辑。调用频率低，可用来处理当需要针对重连玩家发送重连数据时候使用。
- 必须存在命名空间（namespace）。

### 3. 命名规范
- 代码文件：大驼峰，如 `GamePlayEvent`。
- 常量：全大写，如 `HORIZONTAL_SPACE`。
- 函数：大驼峰，如 `CalculateLayout()`。
- 公共变量：大驼峰，如 `string[] NameList`。
- 私有变量：小驼峰，如 `runSpeed = 360f`。

### 4. 事件命名规则
- `SE_`：服务端 System 事件
- `SM_`：服务端全局事件
- `CE_`：客户端 System 事件
- `CM_`：客户端全局事件

事件注册使用固定格式，如：固定 `OnXXXXXXXX`，例如：

```csharp
mySystem.Register<SE_GPO.Event_DownHP>(OnDownLife);
```

## 项目开发规范

### 一、代码结构与抽象规则 (Architecture & Abstraction)

- **R1**：禁止基于“复制粘贴 + 条件分支”的行为扩展。
  - 判定：多个行为/技能仅在速度、仇恨、数值上不同，却存在结构一致的重复代码块。
  - 原则：行为差异是数据问题，不是代码问题。应通过“行为标识 → 数据映射”实现数据驱动。

- **R2**：System 层不得承载业务逻辑。
  - 判定：System 内出现伤害计算、状态判定或具体玩法规则。
  - 原则：System 仅负责组件组合、生命周期桥接与协议封装。它是“搭积木的手”，不是“积木本身”。

- **R3**：功能高度相似的组件必须抽象（R8 整合）。
  - 判定：多个组件仅为了适配不同的 Transform 同步或微小表现差异而独立存在。
  - 方向：参考通用表现组件（如 `PlayEffect`），抽象出通用逻辑，通过配置区分表现。

### 二、生命周期与时序强约束 (Lifecycle & Timing)

- **R4**：严格遵守生命周期职责边界（R3 整合）。
  - 规范：
    - `OnAwake`：仅限事件注册（SE_ CE_ SM_ CM_）、变量初始化、组件挂载。禁止派发事件。
    - `OnStart`、`OnSetEntityObj`：逻辑启动、状态生效、RPC 调用、事件派发。但禁止注册事件。
  - 注：`AddUpdate` 可以选择放在 `OnStart` 或 `SetEntityObj`，但整个组件内只能有一个。
  - 原则：生命周期是契约，违反时序会导致事件丢失或逻辑空转。OnStart、OnSetEntityObj 全局一定只会调用一次。

- **R5**：禁止在不稳定阶段执行网络行为（R4 整合）。
  - 规范：RPC 和 Dispatcher 严禁放在 OnAwake 或 AddComponent 阶段。
  - 原则：未完成内部初始化的系统，不允许对外“发声”。

### 三、数据所有权与同步规则 (Data & Sync)

- **R6**：
  - 常规组件不得直接访问外部配置数据，最好是以 InitData 的方式注入数据到组件，原因：system 主导决定 component 的作用。
  - SceneGPO 组件的数据源，如果涉及到获取列表的，可以用 `GetComponentsInChildren<SceneGPOTimestampBase>` 的方法进行数据列表的获取。
  - 如果只获取一个，如 `config = gameObject.GetComponentInChildren<SceneGPOPathGenerator>()`，就需要直接在 awake 里面通过 `var initData = (ServerAISceneGPOSystem.InitData)initDataBase; config = (SceneGPOPathGenerator)initData.Data;` 的方式获取数据。
  - 原因：SceneGPO System 的组件是动态增加的，增加的依据本身就是对应数据源文件。所在在组件创建的时候数据源就已经进行设置，不需要再获取一次。

- **R7**：统一使用标准同步组件（新增）。
  - 规范：严禁自定义 Position/Rotation/ScaleSync。
  - 方向：统一使用 `ServerNetworkTransform` 和 `ServerNetworkSync`，避免重复造轮子并解决潜在同步 BUG。

- **R8**：配置缺失必须被显式处理（R6 整合）。
  - 判定：动态加载资源后未判空直接使用。
  - 原则：资源缺失必须触发 Assert 或 Error 日志。配置错误不应引发 Crash。

### 四、性能与缓存规则 (Performance & Optimization)

- **R9**：`Update`/高频路径禁止高 GC 函数调用。
  - 禁止：`GetComponent`、`GameObject.Find`、`new`（只允许 new 事件相关（SM_ CM_ SE_ CE）） 对象、字符串拼接 (`string.Concat`)。
  - 方向：在 Init 阶段缓存引用；高频 ID 使用常量而非拼接字符串。

- **R10**：循环体内严禁重复索引访问（R14 整合）。
  - 规范：`list[i]`、`dict[key]` 在循环内必须先缓存为局部变量。
  - 原则：减少底层索引开销，提升循环效率。

- **R11**：禁止深层链式调用（R10 整合）。
  - 判定：出现 `xx.xx.xx().xx` 超过三层的调用。
  - 原则：深层调用不仅可读性差，且极易引发空指针异常（NullReferenceException）。

- **R12**：`Select`、`OrderBy`、`ToList`、`ToArray` 禁止在 Update 中每帧调用。

### 五、逻辑安全性与严谨性 (Safety & Robustness)

- **R13**：随机逻辑必须可控（R11 整合）。
  - 规范：`while + Random` 必须有最大尝试次数或明确退出条件。
  - 判定：移除列表元素前未校验 Count。
  - 原则：防止因配置异常导致服务端死循环。

- **R14**：硬编码值必须语义化（R12 整合）。
  - 规范：禁止无注释的硬编码索引（如 `index = 0`）。
  - 原则：硬编码等于隐式规则，必须由设计确认并常量化。

### 六、内存管理与清理规则 (Memory Management)

- **R15**：`Init / Clear` 必须成对且收敛（R15 整合）。
  - 规范：Init 中 Add 的事件、New 的集合、赋值的 Action，在 Clear 中必须注销或清空。
  - 原则：不可见的引用最危险。仅将引用置 null 而不清理集合是内存泄漏的主因。

### 七、其他专项规则 (Special Rules)

- **R17**：变量与枚举定义位置规范。
  - 规范：枚举置顶，变量紧随其后。严禁变量插在函数中间。
  - 原则：提升代码扫描效率，符合团队统一审美。

- **R18**：Editor 工具代码隔离。
  - 规范：涉及 `GameObject.Find` 或临时探针创建的工具逻辑，必须确保只在 Editor 下执行，且有明确的销毁路径。

- **R19**：禁止创建“空 Entity”兜底（R7 整合）。
  - 规范：不允许通过 `CreateEntity("EmptyServer")` 来规避逻辑漏洞。
  - 原则：实体不存在是业务逻辑问题，应从调用源头拦截。

- **R20**：对象所有权与销毁权限收敛规则。
  1. **核心规则**
     - 核心逻辑：A 创建 B，A、B 均有销毁的权力，C 创建了 B，A 只有监听权没有销毁权。
     - 归口管理：若 A 组件（或 System）负责创建了 B System，则 A 拥有对 B 的绝对控制权，包括发起销毁指令。
     - 内部自律：B System 内部的组件应负责监听自身的销毁状态，并在销毁时派发事件。
     - 外部从动：非创建者（其他关联组件）仅允许监听销毁事件并执行自身的清理逻辑（如解绑、置空引用），禁止主动触发 B 的销毁。

  2. **判定标准（Bad Cases）**
     - 【越权销毁】A 并没有生成 B，但通过监听 B 的某个业务状态（如血量归零、倒计时结束），直接调用了 B 的销毁方法。
     - 【职能混淆】B System 已经拥有完善的自销毁逻辑，但外部多个组件都在尝试调用销毁接口，导致销毁回调被触发多次。

- **R21**: 组件内可以使用 `MsgRegister` 进行全局事件派发。
- **R22**: 组件命名不能带 Manager 或 System。
- **R23**: 组件内持有的公共数据结构，只能是模板数据，Data 类、事件类（SM CM SE CE）里的公共数据结构，不能是其他组件的数据结构。
