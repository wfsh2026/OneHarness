# 项目审核规范

> **角色归属**：本文件由 **项目负责人 Agent** 专属使用。
> **维护责任**：每次协作规则变更后，项目负责人必须同步更新本文件，并通过 `session-sync.sh` 记录变更内容。变更后立即在 `active.md` 归档更新记录。
> **规范权威来源**：本文件审核条目来自 [[workflow-dev]]，以本文件为权威执行索引。

## 零、多 Agent 分工合规清单 (Round 0)

**审核触发条件**：DL 完成「需求拆解执行计划草稿」后，**在 Round 1 内容审核之前**，优先执行此项检查。

**审核目的**：确认 DL已正确判断功能复杂度，并将应当分发给专职 Agent 的任务进行了分发，而非自己全部包揽。

### R0 判定标准：何时必须启用多 Agent 协作

下列条件满足**任意一条**，DL 必须将对应任务分发给专职 Agent：

| 条件 | 必须分发给 |
|------|----------|
| 功能需要新建独立 GPO 类型（AI 单位/SceneGPO/拾取物等） | GPO Programmer |
| 功能需要新建 AB 或 AE（子弹/爆炸/持续效果等） | Ability Programmer |
| 功能需要新建 Unity 场景或修改场景层级结构 | Scene Builder |

**例外**：若功能只涉及**纯模式逻辑**（不涉及新 GPO/新 Ability/新场景），DL可独立完成，不需要分发。

### Round 0 审核清单

| 编号 | 审核项 | 要求内容 | 不通过处理 |
|------|--------|---------|----------|
| R0-01 | 复杂度评估 | DL 的草稿中是否包含"是否需要多 Agent 协作"的明确判断（即使判断为"不需要"也必须有说明） | 退回 DL，要求补充判断 |
| R0-02 | GPO 分发 | 若功能涉及新 GPO，是否已在「子任务分发说明」中指派给 GPO Programmer | 退回 DL，要求重新规划，将 GPO 开发分发出去 |
| R0-03 | Ability 分发 | 若功能涉及新 AB/AE，是否已在「子任务分发说明」中指派给 Ability Programmer | 退回 DL，要求重新规划，将 Ability 开发分发出去 |
| R0-04 | 场景分发 | 若功能涉及新场景，是否已在「子任务分发说明」中指派给 Scene Builder | 退回 DL，要求重新规划，将场景建设分发出去 |
| R0-05 | 预留桩规范 | 若 DL自己写了涉及其他 Agent 领域的代码，该部分是否以预留桩形式存在（`// TODO: [等 XXX Agent 确认]`），而不是自行假设接口 | 退回 DL，将假设接口改为预留桩 |
| R0-06 | **开发计划文档路径合规** | 开发计划文档必须存放在 `docs/GamePlay_Dev/{功能名}/{功能名}开发计划.md`；**禁止**存放在 `session-state/`、`agents/` 或其他路径 | 退回 DL，要求迁移到正确路径后重新提交 |
| R0-07 | **开发计划范围完整性** | 开发计划必须覆盖功能**全生命周期**（M-02 含所有 Phase，非仅单 Phase）；Phase × 体验节点交替排列格式必须存在 | 退回 DL，补充完整阶段和体验节点 |
| R0-08 | **技术子文档框架是否已创建** | DL 必须已在 `docs/GamePlay_Dev/{功能名}/技术文档/` 下创建所有子文档空框架（README.md + 各专职文档骨架），且已在主计划 M-03 中列出索引 | 退回 DL，要求补充创建子文档空框架 |

**通过条件**：R0-01 至 R0-08 全部 ✅，才能进入 Round 1。

**打回说明**：项目负责人只负责指出缺失的分发，**不参与任务分配的决策**。打回后由 DL 自行重新规划分发方案。

## 一、阶段2 DL 草稿审核清单 (Round 1)

**审核触发条件**：DL 完成「需求拆解执行计划草稿」后，**Round 0 通过后**，再执行本轮审核，发给用户前必须经过此审核。

**审核依据来源**：`workflow-dev.md` → 阶段2「强制守则第7条」DL 必须包含内容。

| 编号 | 审核项 | 要求内容 | 检查方式 |
|------|--------|---------|---------|
| R1-01 | 会话预检报告 | 包含：系统识别结果（涉及哪些系统）+ 歧义检查（是否有"武器/飞行物/跟随体"等需要额外确认的情况）| 检查是否有系统归属说明 |
| R1-02 | 初步系统归属评估表 | 每个功能点对应哪个系统（GPO/模式/枪械/Ability/镜头/UI/事件等）| 检查是否有逐功能归属的表格 |
| R1-03 | 关键技术方案选项 | 至少一个关键决策点提供了**多方案对比**（≥2个方案），供用户阶段3选择 | 检查是否有"方案A/方案B"格式的选项 |
| R1-04 | 技术可行性评估 | 包含：主要风险点（≥1条）+ 对应的规避方案 | 检查是否有风险清单 |
| R1-05 | 新发现歧义点列表 | 明确列出策划案中存在的、需要在阶段3拍板的不确定内容（即使为空也需说明"无歧义"）| 检查是否有歧义列表 |
| R1-06 | GD 模糊点清单 | 对照 `设计文档完整性思维框架.md` 列出：几何尺寸/弹道参数/成长曲线等开发所需的精确数值是否完整 | 检查是否有分类的模糊点说明 |
| R1-07 | GD 体验优化建议 | 包含：核心循环评估 + 初始数值提案（哪怕是区间值）| 检查是否有数值建议 |

**通过条件**：R1-01 至 R1-07 全部 ✅。

## 二、阶段4 最终文档审核清单 (Round 2)

**审核触发条件**：GD 完成「完整策划案.md」、DL 完成「需求开发执行计划文档.md」后，发给用户前必须经过此审核。

### 2.1 完整策划案.md 审核

**审核依据来源**：`设计文档完整性思维框架.md` + `workflow-dev.md` 阶段4。

| 编号 | 审核项 | 要求内容 |
|------|--------|---------|
| R2-01 | 几何尺寸完整性 | 所有新建 GPO/场景对象均有精确的宽/高/深尺寸（单位：m），不允许"参考XXX大小"等模糊描述 |
| R2-02 | 弹道/速度参数完整性 | 涉及抛射物的功能均有：初始速度、终末速度、变化曲线（线性/指数）三项数值 |

| R2-04 | 异常边界定义 | 核心机制（如：Buff叠加/基地满血治疗/复活无敌等）的边界情况有明确的处理描述 |
| R2-05 | 胜负条件闭环 | 所有胜利/失败/平局的触发条件均有明确定义，无遗漏的判定盲区 |

### 2.2 需求开发执行计划文档.md 审核

**审核依据来源**：`workflow-dev.md` 阶段4「必须包含的四项内容」+ 阶段5「五项强制审阅清单」。

| 编号 | 审核项 | 要求内容 |
|------|--------|---------|
| R2-06 | ★开发阶段×体验节点流程图 | 文档**最顶部**必须有此 ASCII 流程图，格式：Phase → ★体验节点 → Phase 交替排列 |
| R2-07 | 体验节点完整性 | 每个体验节点必须包含：可体验内容描述 + 核心感受验证问题 + 用户确认后进入下一 Phase 的说明 |
| R2-08 | 灰盒资源占位方案 | 每个新视觉对象（GPO/特效/UI）必须有：形状 + 颜色（RGBA 或颜色名）+ 尺寸（单位：m）+ 挂点/特殊设置。不接受"Cube 占位"而缺少后三项 |
| R2-09 | UI 灰盒方案 | 所有 HUD 元素和界面均有独立的灰盒描述（不可归入"待定"）|
| R2-10 | 核心循环完整性 | 至少一条链路完整描述：玩家输入 → UI → CMD → 服务端 → RPC → 客户端表现 |
| R2-11 | 关键交互链路图 | 涉及玩家主动操作的功能（点击/选择/开火/拾取等）均有 ASCII 链路图 |
| R2-12 | 文件清单完整性 | 新增文件、修改文件均已列出，每项有：完整路径 + 功能说明 + 新建/修改标识 |
| R2-13 | 场景文件 | 若涉及新地图，客户端场景和服务端场景均已在文件清单中列出，生成方式已说明 |
| R2-14 | 架构决策归档 | 所有在阶段2-3中用户拍板的技术决策均已在执行计划中归档 |
| R2-15 | 验收清单 | 包含每个 Phase 的可验证测试项（每项具体可操作，不得只写"功能正常"）|

**通过条件**：R2-01 至 R2-15 全部 ✅。

## 三、审核失败处理规则

1. **单项不通过**：列出具体的 ❌ 项，要求对应的 GD/DL补充，不得绕过。
2. **多项不通过**：一次性列出所有 ❌，由 GD/DL统一补充后再次提交。
3. **补充后审核**：只复核 ❌ 项，已通过的 ✅ 项无需重新核对。
4. **最终放行**：所有项 ✅ 后，输出"审核通过"，文档可发给用户。

## 四、审核范围说明

| 审核范围 | 包含 | 不包含 |
|---------|------|-------|
| ✅ 文档结构完整性 | 必要章节是否存在 | 内容的创意质量 |
| ✅ 数值精确性 | 数值是否具体可量化 | 数值是否最优 |
| ✅ 链路完整性 | 交互链路是否从头到尾 | 架构方案是否最合理 |
| ✅ 规范合规性 | 是否遵循开发工作流文档的要求 | 代码实现细节 |

## 五、多文档结构审核规范（Plan-Doc Mode）← 2026/坦克大乱斗重构 新增

> 当 DL 启用「主计划 + 多子文档」体系时，项目负责人在 Round 2 审核中额外执行本节规范。

### 5.1 多文档验收顺序

```
Step 1：先审主计划结构（M-01~M-05 五项，见下方清单）
   │  ↓ 通过后
Step 2：逐一审核每份子文档的九大要素（S-01~S-09，见下方清单）
   │  ↓ 每份通过后才审下一份
Step 3：所有子文档通过后，执行跨文档一致性检查（X-01~X-04）
   │  ↓ 全部通过
输出：多文档体系审核通过，可发给用户
```

### 5.2 主计划文档审核清单

| 编号 | 审核项 | 要求内容 | 检查方式 |
|------|--------|---------|---------|
| MD-M-01 | 游戏主循环结构图 | ASCII 图存在，节点标注子系统名称与子文档索引 | 检查文档顶部是否有 ASCII 游戏循环图 |
| MD-M-02 | 体验节点总览 | Phase 分期完整，每 Phase 含体验目标和用户确认节点 | 检查是否有 Phase×体验节点交替排列的总览 |
| MD-M-03 | 交付物表 | 每条交付物链接到具体子文档 | 检查每 Phase 的交付物是否有对应子文档链接 |
| MD-M-04 | 验收标准 | 每 Phase ≥1 条可测试行为描述验收项 | 检查是否有验收 checklist |
| MD-M-05 | 子文档索引 | 列出全部子文档，含版本、职责范围、摘要 | 检查是否有完整的子文档索引表 |

**通过条件**：MD-M-01 至 MD-M-05 全部 ✅。

### 5.3 子文档九大要素审核清单

| 编号 | 要素 | 合规条件 | 常见不通过情形 |
|------|-----|---------|-------------|
| MD-S-01 | 作者签署 | 元信息 `>` 区块含 `**负责 Agent**` + `**Agent 定位**：\`...\`（已熟读）` | 缺 Agent 定位字段，或未写（已熟读） |
| MD-S-02 | 参考文档 | 表格含三类条目（开发范例 / 边界定义 / 规则文件），无则写「暂无」 | 缺某一类条目行；或声明"暂无"但可用资源清单中存在对应文档 |
| MD-S-03 | 功能需求 | 一句话玩家视角体验描述 | 缺该段落，或内容是技术描述而非玩家体验 |
| MD-S-04 | 功能定位 | 有独立段落说明职责边界 | 只写功能名，无职责边界描述 |
| MD-S-05 | 文件清单 | 分层表格（📋/🔀/🖥️/💻/🎨），每条目含 `**新建**`/`**修改**` 标注 | 缺 CSV 数据行；状态标注为"待定"；只写路径不写操作类型 |
| MD-S-06 | ASCII 交互链路图 | 核心流程时序图；涉及玩家操作时覆盖 `输入→CMD→服务端→RPC→客户端表现` 完整链路 | 只有文字描述，无图；或链路缺少关键节点 |
| MD-S-07 | 灰盒资源占位 | 每个新视觉对象：形状/颜色/尺寸/挂点偏移 四项齐全 | 无新视觉对象时写 N/A；有新对象但缺其中任一项 |
| MD-S-08 | 边界条件 | 外部依赖 + 禁止行为 + 边界文档引用 三项齐全 | 缺"禁止行为"或无文档引用 |
| MD-S-09 | 验收标准 | `- [ ]` 清单覆盖编译/运行时/功能三层，每条是可执行行为描述 | 验收项是代码描述（如"调用 Spawn 方法"）而非行为描述；或未分三层 |

**通过条件**：每份子文档的 MD-S-01 至 MD-S-09 全部 ✅（MD-S-07 无新视觉对象时填 N/A 视为通过）。

### 5.4 ADR 章节审核清单

**触发条件**：技术实现与主计划原始方案不同时，子文档末尾必须有 ADR 章节。项目负责人发现差异但无 ADR → 直接打回。

| 编号 | 审核项 | 要求内容 |
|------|--------|---------|
| MD-A-01 | 变更类型 | 明确分类（GPO类型变更/System重构/协议调整等） |
| MD-A-02 | 原方案与新方案 | 两者均有描述，差异清晰 |
| MD-A-03 | 变更原因 | 有技术原因说明（不可为空） |
| MD-A-04 | 用户授权声明 | 明确写明经用户确认，含日期或会话标识 |
| MD-A-05 | 影响范围 | 列出受影响的文件/系统 |

### 5.5 跨文档一致性检查清单

| 编号 | 检查项 | 判定标准 | 打回条件 |
|------|--------|---------|---------|
| MD-X-01 | Rpc 发送主体 | 同一 Rpc 在多份文档中，发送方（Server/Client）一致 | 发现矛盾即打回所有涉及该 Rpc 的子文档 |
| MD-X-02 | GPO 类型声明 | 跨文档引用同一 GPO，类型名完全一致 | 同一 GPO 在不同文档中类型名不同即打回 |
| MD-X-03 | System 状态标注 | 同一 System 在不同子文档的状态（新建/修改）不矛盾 | 状态矛盾即打回双方文档要求统一 |
| MD-X-04 | 文件清单重复声明 | 同一 .cs 文件不在多份子文档中均标"新建" | 发现重复"新建"声明即打回要求明确归属 |
