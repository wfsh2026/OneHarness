# 系统地图与检索指导 (system-map-rules.md)

> 本文件定义**通用检索规则和会话执行协议**。
> 项目特定的系统地图、实例清单、文档索引见 [[knowledge/system-map]]。
> 
> **规则优先级**：[[knowledge/system-map]]（项目数据）> 本文件（通用规则）> 其他规范文件

---

## 一、强制预检流程（每次会话必须输出）

**【强制】** 在回答任何用户请求、生成任何代码之前，必须先输出以下格式的预检报告：

```
【会话预检】
① 涉及系统：[列出识别到的系统，如：GPO系统 / 模式系统 / Ability系统]
② 已加载文档：
   - system-map.md ✅
   - [[INDEX]] ✅
   - [系统边界定义文档名] ✅ / ❌ 未找到（降级处理）
③ 歧义检查：
   - 是否涉及"武器/飞行物/悬浮体/跟随体"？→ 需询问 GPO 还是外观包装
   - 是否涉及"刷怪/波次/生成单位"？→ 先检索 T-GPOSpawner 可复用性
   - 核心循环是否包含玩家主动交互？→ 需完成核心循环完整性 Checklist
```

**不输出预检报告不得开始生成代码。**

## 二、意图识别规则（通用框架）

收到用户请求后，扫描关键词，识别涉及的系统，决定加载哪些文档。

> 具体关键词 → 系统映射表见各项目的 [[knowledge/system-map]]。
> 意图识别认知框架见 [[意图识别与系统归属思维框架]]。

### 识别原则

1. **一句话可能涉及多个系统**——每个识别到的系统都要加载对应文档
2. **关键词有歧义时**：GPO 系统是最常见的入口，优先检查 GPO 边界定义是否能覆盖
3. **不确定涉及哪个系统时**：主动向用户确认，不要猜测
4. **"武器/飞行物/悬浮体/跟随体"歧义识别**：遇到这类需求时，**不得直接判断系统归属**，必须先向用户询问"这是独立 GPO 单元还是现有系统的外观包装"
5. **"刷怪/波次/生成"类需求**：在意图识别阶段同时检索现有 GPO 生成器框架是否可复用，不得直接创建新 System

## 三、会话执行协议

### 3.1 单系统请求（简单场景）

```
0. 输出【会话预检】报告（强制）
1. 读 system-map.md（本文件 + knowledge/system-map.md）
2. 识别涉及系统
3. 加载 harness/rules/ 对应系统规范文档
4. 理解用户意图
5. 如有不确定项，一次性列出疑问，等待用户回答
6. 执行生成
7. 汇报生成结果（新建/修改了哪些文件）
```

### 3.2 多系统请求（跨域场景）

当用户一句话涉及多个系统时，必须先拆解，再按依赖顺序生成：

**第一步：拆解请求**

输出标准格式：

```
【需求理解】
原始需求："[用户原文]"

【拆解结果】
子任务 1 - [系统名]：[具体要做什么]
  依赖：无（独立）

子任务 2 - [系统名]：[具体要做什么]
  依赖：子任务①完成后

跨系统通信：[系统A] 通过 [EventDirector/消息类型] 通知 [系统B] 发生了 [什么事件]

【执行顺序】
① → ②（②依赖①）

【待确认项】（如有）
- [需要用户确认的参数或设计决策]
```

**第二步：等待用户确认拆解后再开始生成**

**第三步：按顺序逐系统生成**，每完成一个子任务汇报进度

## 四、核心循环完整性检查

> **完整 Checklist 和交互链路图格式见** [[gpo-code]]。

在输出「需求拆解」和「执行计划」时，**必须对核心循环做完整性检查**。核心要点：

- **若玩家需要点击/选择/确认**，则 UI 交互链路属于核心循环，**不得延后**
- 执行计划必须包含完整的 `玩家输入 → UI → CMD → 服务端 → RPC → 客户端表现` 链路图
- 若链路图缺失，阶段2文档化不得通过

---

## 五、缺失边界定义文档的降级处理

当用户请求涉及某系统，但该系统的**边界定义文档尚未建立**时：

**降级步骤：**

1. 加载该系统的**范例文档**（`aigc/wiki/raw/biu2-framework/范例文档/` 目录下）
2. 加载 [[GamePlay_Dev/README]] 确认按需加载规范
3. **必须在回复开头向用户说明**：
   > "「[系统名]」的能力边界文档尚未建立，我将基于范例文档推断实现方式。以下方案仅供参考，请在确认方向后继续。"
4. 不得自行发明该系统的新架构或父类
5. 完成生成后，建议用户为该系统建立边界定义文档

**不确定时的处理原则：**

- 宁可提问，不猜测
- 一次性列出所有疑问（不要单独问一个，再问下一个）
- 对于参数数值类问题：AI 提供建议值，用户最终确认

## 六、生成顺序原则

**被依赖的系统优先生成。** 具体系统依赖关系见各项目的 [[knowledge/system-map]]。

通用原则：

| 优先级 | 说明 |
|-------|------|
| 1（最先） | 基础数据系统（GPO / 枪械等被其他系统依赖的） |
| 2 | 逻辑系统（Ability / 载具等依赖基础数据的） |
| 3（最后） | 编排系统（模式等依赖所有子系统就位后组装的） |

## 七、大规模实例系统的分层索引规则

> 当某个系统拥有大量实例（如 Buff 245 个），无法在 system-map §三 逐行列出时，需采用分层索引策略。

### 7.1 核心原则：正向可达

**Agent 从 system-map 出发，必须能正向到达任何一个 feature。** 禁止仅依赖反向依赖链（如 buff-gold-dash-get-site → buff-framework ← system-map）。

### 7.2 消费者挂载规则（优先）

**功能专属实例必须挂到消费者 feature 上。**

- 若实例仅被一个功能使用（如 `buff/golddash` 仅被 GoldDash 模式使用），则将实例列表作为「关联 Buff」/「关联实例」段落追加到消费者 feature 文件中
- 链路：`system-map §三 → 消费者 feature → 具体实例`（**2 跳可达**）
- 消费者判定依据：实例的 `category` 子类型与消费者 feature 的功能域一致

**判定规则：**

| category 模式 | 消费者 feature | 示例 |
|--------------|---------------|------|
| `buff/{模式名}` | 对应 mode feature | buff/golddash → mode-golddash |
| `buff/{身份卡名}` | 对应 idcard feature | buff/ganda → idcard-ganda |
| `buff/{通用分类}` | 框架 feature | buff/combat → buff-framework |

### 7.3 独立分类索引规则（兜底）

当实例无法确定消费者 feature 时（如 category 对应的 mode/idcard 不存在），使用独立分类索引文件：

- 命名：`_index-{系统}-{分类}.md`（前缀 `_` 表示自动生成的索引）
- 放在同目录下
- 内容：表格列出该分类下所有实例的 `[[wiki-link]]`
- system-map §3.x 指向该索引

### 7.4 §二 意图识别表精确制导规则

**§二 的每一行必须指向最精确的目标**，不得用中间层替代：

| 场景 | ✅ 正确 | ❌ 错误 |
|------|---------|--------|
| 搜具体 buff 关键词 | `[[buff-add-hp-for-time]]` | `[[buff-framework]]`（太泛） |
| 搜某功能全部 buff | `[[buff-pve-monster]]`；全部见 `[[mode-pverogue]]` | 只给 `[[mode-pverogue]]`（丢失直接命中） |
| 搜框架级概念 | `[[buff-framework]]` | 具体实例（太窄） |

**禁止行为：**
- ❌ 禁止 §二 的目标列指向分类索引或 framework 让 Agent 自己翻找
- ❌ 禁止为了指向消费者而丢失对具体实例的直接引用
- ✅ 精确命中 + 全量浏览两个信息可以同时给出

### 7.5 维护方式

大规模实例的分层索引（消费者挂载、独立分类索引）由 AI 在增量更新时手动维护：
- 新增 buff → 手动追加到消费者 feature 的「关联 Buff」段落
- 新增分类且无消费者 → 手动创建 `_index-{系统}-{分类}.md`
