# 1 代架构网络消息制作规范

> **适用范围**：GamePlay 网络层 — 新增协议定义、C/S 网络功能模块、消息路由与序列化
> **不适用**：Mirror 框架底层 → 归第三方库；HTTP/WebSocket → 归 Utils 层；大厅网络 → 归 Lobby 层
> **参考实现**：Proto_Camera（简单协议 4 消息）、Proto_GoldDash（复杂协议 30+ 消息）

---

## 一、架构概述

### 1.1 核心类依赖

```
ProtoClient (Client/Network/Proto/ProtoClient.cs)
  │  职责: 客户端协议路由总线，注册 60+ Feature 模块
  │  初始化: AddFeature<NetworkClient_{Feature}>() 逐一注册
  │
  ├── NetworkClient_{Feature}_Base.cs (Client/Network/Base/Feature/)
  │     ★ 自动生成，注册消息监听回调
  │     继承: NetworkClientMsgBase
  │     调用: AddHandler(Proto_{Feature}.XxxRpc.ID, OnXxx)
  │
  └── NetworkClient_{Feature}.cs (Client/Network/Feature/)
        ★ 手动实现，处理 Rpc 回调 + 发送 Cmd
        继承: NetworkClient_{Feature}_Base
        方法: OnXxxRpc() 处理服务器推送

ProtoServer (Server/Network/Proto/ProtoServer.cs)
  │  职责: 服务端协议路由总线，注册 60+ Feature 模块
  │
  ├── NetworkServer_{Feature}_Base.cs (Server/Network/Base/Feature/)
  │     ★ 自动生成，注册 Cmd 监听
  │
  └── NetworkServer_{Feature}.cs (Server/Network/Feature/)
        ★ 手动实现，处理 Cmd + 发送 Rpc/TargetRpc

Proto_{Feature}.cs (Host/Network/Proto/Base/)
  │  ★ 自动生成（从 .txt 定义文件）
  │  包含: ICmd / IRpc / IClientRpc / ITargetRpc 结构体定义
  │  共享: 三端（Host/Client/Server）共用
  │
  └── Proto/Base/Struct/ (400+ ProtoStruct 辅助类)
        ★ 自动生成，复杂数据结构的序列化/反序列化

ByteBuffer / ByteBufferPool (序列化层)
  │  二进制读写：WriteByte/WriteInt/WriteFloat/WriteLossyVector3...
  │  池化管理：ByteBufferPool.Get() / Release()
  │  压缩：ZstdUtils.Compress/Decompress
  │
  └── 报文格式: [API_ID:1byte][FUNC_ID:1byte][payload:N bytes]
        分包阈值: 450 bytes (MTU限制)
        带宽限制: 80KB client-side rate limit
        批次窗口: 0.3s batch window
```

### 1.2 三种消息接口

| 接口 | 方向 | 说明 | 典型场景 |
|------|------|------|---------|
| **ICmd** | C→S | 客户端发往服务器的命令 | 移动、射击、使用道具 |
| **ITargetRpc** | S→指定C | 服务器发给特定客户端 | 个人数据更新、错误反馈 |
| **IClientRpc** (IRpc) | S→全体C | 服务器广播给所有客户端 | 状态同步、全局事件 |

### 1.3 QoS 类型

| 值 | 枚举 | 说明 | 使用场景 |
|-----|------|------|---------|
| **0** | ReliableSequenced | 可靠有序，保证送达 | 登录、道具操作、状态切换 |
| **1** | UnreliableSequenced | 不可靠有序，允许丢包 | 移动同步、镜头旋转、高频数据 |

### 1.4 协议编号规则

```
消息 ID = API_ID × 1000 + FUNC_ID

API_ID: 功能域编号（每个 Proto 文件独占一个，如 Camera=12, Item=18）
FUNC_ID: 域内消息序号（从 001 开始自增）

示例：
  Proto_Camera (API_ID=12)
    CmdCameraMoveData        = 12 × 1000 + 1 = 12001
    CmdLookCameraMoveData    = 12 × 1000 + 2 = 12002
    CmdSetLockCameraRole     = 12 × 1000 + 3 = 12003
    CmdFreeLook              = 12 × 1000 + 4 = 12004
```

### 1.6 预制体与资源加载（★）

| 资源 | 路径 | 加载方式 |
|------|------|---------|
| **Proto 定义文件(.txt)** | `Assets/Script/GamePlay/Host/Network/Proto/ProtoTxt/` | 构建时工具读取，生成 Proto_*.cs |
| **Proto_*.cs** | `Assets/Script/GamePlay/Host/Network/Proto/Base/` | 编译时静态引用，无运行时加载 |
| **ProtoStruct_*.cs** | `Assets/Script/GamePlay/Host/Network/Proto/Base/Struct/` | 编译时静态引用 |
| **NetworkClient 模块** | `Assets/Script/GamePlay/Client/Network/Feature/` | ProtoClient.Init() 注册 |
| **NetworkServer 模块** | `Assets/Script/GamePlay/Server/Network/Feature/` | ProtoServer.Init() 注册 |

**初始化时序**：

```
战场加载 → GameWorldManager 初始化
  → ProtoClient.Init() / ProtoServer.Init()
    → 逐一 AddFeature<NetworkClient_{Feature}>()  (60+ 模块)
    → 每个 Feature 构造函数中注册 Handler:
        AddHandler(Proto_{Feature}.XxxRpc.ID, OnXxxRpc)
  → 网络就绪，开始收发消息
```

### 1.7 禁止修改的文件

- **Proto/Base/ 下所有自动生成文件** — 手动改会被覆盖，必须修改 .txt 定义文件后重新生成
- **Proto/Base/Struct/ 下所有 ProtoStruct 文件** — 同上，自动生成
- **ProtoClient.cs / ProtoServer.cs 的注册顺序** — 影响初始化依赖

## 三、配置文件详解

### 3.1 Proto 定义文件（.txt 格式）

**路径**：`Assets/Script/GamePlay/Host/Network/Proto/ProtoTxt/{API_ID}_{Feature}.txt`

**格式示例**（以 Camera 为例）：

```
# API_ID = 12
# Feature = Camera

# Cmd: Client → Server
CmdCameraMoveData 12001 ICmd QoS=1
    Vector3 rota lossy          # Lossy Vector3 压缩，仅 3 字节
    byte cameraRatioLevel       # FOV 级别 0-3

CmdLookCameraMoveData 12002 ICmd QoS=1
    Vector3 rota lossy

CmdSetLockCameraRole 12003 ICmd QoS=0
    int roleId

CmdFreeLook 12004 ICmd QoS=0
    bool isFreeLook

# TargetRpc: Server → 指定 Client
TargetRpcLookCameraMoveData 12002 ITargetRpc QoS=0
    int roleId
    Vector3 rota lossy
    Vector3 lookRota lossy
    bool isFireState
    bool isHuXi
    float cameraRatioLevel

# Rpc: Server → All Clients
RpcFreeLook 12004 IRpc QoS=0
    bool isFreeLook
```

**关键规则**：
- API_ID 必须全局唯一，新功能需向团队申请编号
- FUNC_ID 在 API_ID 域内从 001 自增，不可复用已删除编号
- Cmd 和对应的 TargetRpc/Rpc 可以共享 FUNC_ID（方向不同）
- QoS=0 可靠有序（状态变更），QoS=1 不可靠（高频同步）

### 3.2 ByteBuffer 字段类型表

| 写入方法 | 读取方法 | C# 类型 | 字节数 | 说明 |
|---------|---------|--------|--------|------|
| `WriteByte(v)` | `ReadByte()` | byte | 1 | 枚举、标志位 |
| `WriteBool(v)` | `ReadBool()` | bool | 1 | 布尔值 |
| `WriteShort(v)` | `ReadShort()` | short | 2 | 短整数 |
| `WriteInt(v)` | `ReadInt()` | int | 4 | 通用整数、ID |
| `WriteFloat(v)` | `ReadFloat()` | float | 4 | 浮点数 |
| `WriteLong(v)` | `ReadLong()` | long | 8 | 大数、时间戳 |
| `WriteVector3(v)` | `ReadVector3()` | Vector3 | 12 | 完整精度坐标 |
| `WriteLossyVector3(v)` | `ReadLossyVector3()` | Vector3 | 3 | 有损压缩旋转（角度→byte） |
| `WriteString(v)` | `ReadString()` | string | 2+N | 2字节长度前缀 + UTF8 内容 |
| `WriteBytes(v)` | `ReadBytes()` | byte[] | 4+N | 4字节长度前缀 + 数据 |

**Lossy Vector3 压缩原理**：
```csharp
// 写入：将 float 角度映射到 byte (0-255)
public void WriteLossyVector3(Vector3 v) {
    WriteByte((byte)(v.x / 360f * 255f));  // X 旋转 → 1 byte
    WriteByte((byte)(v.y / 360f * 255f));  // Y 旋转 → 1 byte
    WriteByte((byte)(v.z / 360f * 255f));  // Z 旋转 → 1 byte
}
// 总共仅 3 字节，精度 ≈ 1.41°，适用于镜头/角色旋转同步
```

### 3.3 生成的 Base 文件结构

**Client Base（自动生成）**：

```csharp
// NetworkClient_{Feature}_Base.cs — 自动生成，勿手动修改
public abstract class NetworkClient_{Feature}_Base : NetworkClientMsgBase {
    protected override void RegisterHandlers() {
        // 自动注册所有 Rpc/TargetRpc 的 Handler
        AddHandler(Proto_{Feature}.TargetRpcXxx.ID, OnTargetRpcXxx);
        AddHandler(Proto_{Feature}.RpcXxx.ID, OnRpcXxx);
    }
    
    // 抽象方法 — 子类必须实现
    protected abstract void OnTargetRpcXxx(ByteBuffer buffer);
    protected abstract void OnRpcXxx(ByteBuffer buffer);
}
```

**Server Base（自动生成）**：

```csharp
// NetworkServer_{Feature}_Base.cs — 自动生成，勿手动修改
public abstract class NetworkServer_{Feature}_Base : NetworkServerMsgBase {
    protected override void RegisterHandlers() {
        AddHandler(Proto_{Feature}.CmdXxx.ID, OnCmdXxx);
    }
    
    protected abstract void OnCmdXxx(int connId, ByteBuffer buffer);
}
```

### 3.4 报文格式与分包

```
┌────────────┬────────────┬──────────────────┐
│ API_ID (1B)│ FUNC_ID(1B)│   Payload (NB)   │
└────────────┴────────────┴──────────────────┘

MTU = 450 bytes
当 Payload > 448 bytes 时自动分包:
  第1包: [API_ID][FUNC_ID][分包标记][包序号0][data 0..447]
  第2包: [API_ID][FUNC_ID][分包标记][包序号1][data 448..895]
  ...接收端按序号重组

压缩: 大包体自动 Zstd 压缩 (ZstdUtils.Compress)
带宽: 客户端 80KB/s 速率限制，0.3s 批次窗口
```

### 4.1 发送 Cmd（Client → Server）

**文件**：业务逻辑代码（任意调用处）

```csharp

    rota = myCamera.rotation.eulerAngles,
    cameraRatioLevel = (byte)currentFovLevel,

```

### 4.2 处理 Cmd 并发送 Rpc（Server 端）

**文件**：`Server/Network/Feature/NetworkServer_{Feature}.cs`

```csharp
public class NetworkServer_{Feature} : NetworkServer_{Feature}_Base {
    
    // Cmd 处理（Client → Server）
    protected override void OnCmd{Action}(int connId, ByteBuffer buffer) {
        // 1. 反序列化
        var data = Proto_{Feature}.Cmd{Action}.Deserialize(buffer);
        
        // 2. 服务器逻辑处理
        var role = GetRole(connId);
        role.{ProcessLogic}(data.{field1});
        
        // 3a. 回复发送者（TargetRpc）
        SendTargetRpc(connId, new Proto_{Feature}.TargetRpc{Response} {
            {resultField} = {resultValue},
        });
        
        // 3b. 或广播所有客户端（Rpc）
        SendRpc(new Proto_{Feature}.Rpc{Broadcast} {
            roleId = role.roleId,
            {stateField} = {stateValue},
        });
    }
}
```

### 4.3 处理 Rpc（Client 端接收）

**文件**：`Client/Network/Feature/NetworkClient_{Feature}.cs`

```csharp
public class NetworkClient_{Feature} : NetworkClient_{Feature}_Base {
    
    // TargetRpc 处理（Server → 本客户端）
    protected override void OnTargetRpc{Response}(ByteBuffer buffer) {
        var data = Proto_{Feature}.TargetRpc{Response}.Deserialize(buffer);
        
        // 更新本地状态
        GameData.{Feature}.{UpdateState}(data.{field});
    }
    
    // Rpc 处理（Server → 所有客户端）
    protected override void OnRpc{Broadcast}(ByteBuffer buffer) {
        var data = Proto_{Feature}.Rpc{Broadcast}.Deserialize(buffer);
        
        // 根据 roleId 找到对应角色并更新
        var role = GameData.FindRole(data.roleId);
        if (role != null) {
            role.{ApplyState}(data.{stateField});
        }
    }
}
```

### 4.5 复杂数据结构（ProtoStruct）

**文件**：如需自定义结构，在 .txt 定义文件中声明

```csharp
// 定义 ProtoStruct（自动生成到 Proto/Base/Struct/）
public struct ProtoStruct_{StructName} : IProtoStruct {
    public int id;
    public Vector3 position;
    public string name;
    
    public void Serialize(ByteBuffer buffer) {
        buffer.WriteInt(id);
        buffer.WriteVector3(position);
        buffer.WriteString(name);
    }
    
    public void Deserialize(ByteBuffer buffer) {
        id = buffer.ReadInt();
        position = buffer.ReadVector3();
        name = buffer.ReadString();
    }
}

// 在消息中使用 ProtoStruct
public struct CmdComplex : ICmd {
    public ProtoStruct_{StructName} data;  // 嵌套结构
    public ProtoStruct_{StructName}[] list; // 结构数组
}
```

## 五、常见问题与踩坑记录

### 5.1 Proto 文件手动修改被覆盖

**现象**：手动修改 `Proto/Base/Proto_{Feature}.cs` 后，下次生成全部丢失

**根因**：Proto/Base/ 下文件由工具从 .txt 定义文件自动生成，每次生成会完全覆盖

**解决方案**：
1. 只修改 `Proto/ProtoTxt/{API_ID}_{Feature}.txt` 定义文件
2. 重新运行生成工具
3. 手动逻辑写在 `NetworkClient_{Feature}.cs` / `NetworkServer_{Feature}.cs`（不带 `_Base` 后缀的文件）

### 5.2 消息到达但不触发回调

**现象**：发送 Cmd 成功，Server 日志显示已处理，但 Client 的 OnXxxRpc 不被调用

**根因**：
- Feature 模块未在 ProtoClient.cs 中注册（缺少 `AddFeature<>()`）
- 消息 ID 不匹配（Cmd 和 Rpc 的 FUNC_ID 对不上）
- Base 文件未重新生成（.txt 改了但没跑生成工具）

**解决方案**：
1. 检查 `ProtoClient.cs` 的 `Init()` 是否包含 `AddFeature<NetworkClient_{Feature}>()`
2. 检查 .txt 定义文件中 Cmd 和 Rpc 的 ID 一致性
3. 重新运行 Proto 生成工具，确保 Base 文件与 .txt 同步

### 5.3 大包体导致丢包

**现象**：发送大量数据（如初始化全部角色状态）时，部分客户端收到不完整数据

**根因**：超过 MTU 450 字节后自动分包，在弱网环境下后续分包可能丢失（尤其 QoS=1）

**解决方案**：
1. 大数据量使用 QoS=0 (Reliable)，不要用 QoS=1
2. 拆分为多条小消息分批发送
3. 使用 ZstdUtils.Compress() 压缩大包体后再发送
4. 检查 80KB/s 带宽限制是否被触发

### 5.4 ByteBuffer 读写顺序不一致

**现象**：反序列化得到的值全是错误数据（但不报错）

**根因**：写入和读取的字段顺序/类型不一致。ByteBuffer 是顺序读写，不带字段名

**解决方案**：
1. 确保 Serialize 和 Deserialize 中字段顺序完全一致
2. 使用自动生成的 Proto 结构体，避免手写序列化
3. 新增字段只能追加到末尾，不能插入中间（兼容性）

### 5.5 频繁发送导致服务器过载

**现象**：某功能上线后服务器 CPU 飙升，大量 Cmd 堆积

**根因**：每帧发送 Cmd 且使用 QoS=0（Reliable），TCP 窗口爆满

**解决方案**：
1. 高频数据（移动/旋转）使用 QoS=1 (Unreliable)
2. 添加发送频率限制（如 0.1s 节流）
3. 合并同类数据，减少包数量
4. 参考 Proto_Camera 的实现：旋转数据 QoS=1 + LossyVector3(3字节)

## 六、验收标准

### 6.1 编译

- [ ] 零 CS error（含自动生成的 Base 文件）
- [ ] Proto 定义文件(.txt) 与生成的 Proto_*.cs 一致
- [ ] ProtoClient/ProtoServer 中已注册新 Feature

### 6.2 配置

- [ ] API_ID 全局唯一，未与已有 Proto 冲突
- [ ] FUNC_ID 在域内唯一，Cmd 与对应 Rpc 的 ID 正确对应
- [ ] QoS 类型选择合理（状态变更=0，高频同步=1）
- [ ] ByteBuffer 字段类型与实际数据匹配

### 6.3 运行时

- [ ] Cmd 发送后 Server 正确收到并处理
- [ ] Rpc/TargetRpc 回调在 Client 端正确触发
- [ ] 弱网环境下核心消息不丢失（QoS=0 的消息）
- [ ] 高频消息（QoS=1）在丢包时不影响核心逻辑
- [ ] 超过 MTU 的消息分包/重组正确

### 6.4 性能

- [ ] 单条消息大小 < 450 bytes（优先不分包）
- [ ] 发送频率合理（非每帧发送或有节流）
- [ ] 客户端带宽 < 80KB/s 限制
- [ ] Vector3 旋转数据使用 LossyVector3 压缩（3 字节 vs 12 字节）
