## 三、执行计划：20 批次模块梳理

### 每批次标准工作流程

```
1. 扫描 → 扫描 Client/Server/Host 三端对应目录结构
2. 识别 → 识别关键类/枚举/接口定义
3. 参考 → 查阅 1 代专属文档（`aigc/wiki/raw/sausage-man/制作文档/` 如有）
4. 填充 → 填写 system-map 对应系统条目 + 创建 feature.json
5. 编写 → 产出 1 代架构制作文档（`aigc/wiki/raw/sausage-man/制作文档/xxx制作.md`）
6. 审核 → 用户确认
```

> ⚠️ 步骤 3 中，仅 `aigc/wiki/raw/sausage-man/制作文档/` 下的文档为有效输入。大多数批次无 1 代文档，需纯代码分析。
> ⚠️ 步骤 5 是新增要求：每个批次必须产出制作文档，格式参考 `载具制作.md`。

```
├── weapon-attach/     ← B11 武器配件功能包（瞄具/弹匣/枪托/枪口/握把/芯片/弹药）
├── role-equip/        ← B12 角色装备功能包（防弹衣/头盔/背包/吉利服/狗牌）
├── idcard/            ← B13 身份卡功能包（冥王/神王/诸葛亮/…）
├── battlefield-item/  ← B14 战场活动道具功能包（活动物品/恶作具/气泡/动作）

├── sub-modes/         ← B19 子玩法功能包
└── infra/             ← B20 基础设施功能包
```

> **`item/` 说明**：道具核心框架（ItemManager/PickItemNet/SplitItem/LootBag）为所有道具类型共享的基础设施，不对应特定批次。各分类功能包在制作时依赖 item-base。
> **`weapon/` → 拆分说明**：原 `weapon/` 目录拆为 `weapon-ranged/`、`weapon-melee/`、`weapon-special/` 三个独立功能包。

## 四、梳理难点与对策

| 难点 | 说明 | 对策 |
|------|------|------|
| **无统一命名空间** | 代码组织依赖目录结构而非命名空间 | 以目录路径作为模块标识 |
| **三端代码分散** | 同一功能分布在 Client/Server/Host 三个目录 | system-map 中用三列标注路径 |
| **模块边界模糊** | 部分模块（如 Features/）是混合功能集合 | 通过代码分析确认归属（不可依赖 2 代边界定义文档） |
| **代码量大** | 仅 Mode 系统就有 1,000+ 文件 | 先扫描目录结构和枚举，不深入每个文件 |
| **缺少架构文档** | 1 代专属文档仅 1 份 | 以代码结构为主要输入，代码即文档 |

## 五、与 2 代的关系

- 两代架构在运行时共存，1 代可能调用 2 代接口
- 部分功能横跨两代（如 Buff 系统、事件系统）
- system-map 中需标注跨代依赖关系
- 详见 [[Gen2-knowledge构建技术方案]]
